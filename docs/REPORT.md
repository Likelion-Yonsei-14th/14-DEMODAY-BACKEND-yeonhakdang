## 2. 선택한 DB와 대안

PostgreSQL을 기본안으로 선택했습니다. 단일 트랜잭션·행 잠금·유일 제약으로 회원/주문/권한/열람/환불의 경합을 처리하고 Flyway로 이관합니다. 로컬 PostgreSQL 17 Compose와 Testcontainers 테스트를 제공합니다.

MySQL 8.4 InnoDB도 업무 요구를 충족합니다. 기존 운영 선호가 없는 상황에서 PostgreSQL UUID/시각·잠금 사용을 기준으로 구현했으며 MySQL 전환에는 타입·DDL·격리수준 검토가 필요합니다. 관리형 서비스의 가격·무료량·리전은 임의로 확정하지 않았습니다. 공급자·백업·복구·TLS·연결 수·리전·위탁/국외 이전은 운영 결정입니다. [비교와 근거](OPERATIONS.md#db-선택).

## 3. 프론트엔드 API와 수정 사항

[전체 계약과 예시](API.md)를 제공합니다. 주요 연동은 `/oauth2/authorization/kakao`, `/api/csrf`, `/api/me/consents`, `/api/results`, `/api/orders`, `/prepare`, `/complete`, `/api/locker`, 상품별 `/open`, `/refunds`입니다.

- `loggedIn`, `purchased`, 최초 열람·환불 여부를 localStorage 플래그로 결정하는 흐름을 서버 응답으로 바꿔야 합니다.
- 두 결제 동의·미성년자 고지·카드 선택, 포트원 SDK와 `checkoutOrder` 모바일 복귀 처리를 추가해야 합니다.
- 결제 완료·‘나중에 보기’에서 open을 호출하지 않고 결과 열기 버튼에서만 호출합니다. 응답 유실 시 실제 표시 여부를 확정할 수 없는 한계는 정책 검토 대상입니다.
- 무료 결과 저장은 오행/학과 ID·점수 최소 요약이므로 기존 화면 전체 재구성에는 버전별 프론트 표 복원이 필요합니다.
- 공개 페이지·가격의 초기 HTML은 존재하지만 사업자 자리표시자·정책 전문 차이·상품 예시를 보완해야 합니다. 실제 GET에서 `/about`과 전달서 개별 상품 경로 3개는 404였습니다. 통합 `/products#...` 경로가 대안 요건을 충족하는지 확인해야 합니다.
- 기존 초대 링크가 이름·생일·출생시간을 Base64로 노출하므로 운영 전 공유 범위와 불투명 토큰 설계가 필요합니다.

실제 PostgreSQL용 `PostgresIntegrationTest`는 같은 서비스 통합 시나리오(파라미터별 실행 포함 27건)를 재사용하며 기본 테스트에서 제외합니다. 현재 환경에는 Docker/로컬 PostgreSQL 실행 파일이 없어 실행하지 않았습니다. Docker 환경에서 `gradlew.bat postgresTest`로 별도 검증해야 합니다. H2 통과를 PostgreSQL 잠금·호환성 검증 완료로 표현하지 않았습니다.

프론트팀 요청에 따라 `https://yeonhakdang.vercel.app`과 `http://localhost:3000`의 credentialed CORS·preflight·401 응답 헤더, 미허용 Origin 차단을 추가 검증했습니다. 이전 해커톤 저장소의 Render/Docker 구성을 참고하여 Dockerfile, 배포 포트, 공개 상태 확인 API를 준비했습니다. Docker 이미지 실행과 실제 배포는 미실행이며 공개 서버 주소는 아직 없습니다. 전달 자료는 [FRONTEND_HANDOFF.md](FRONTEND_HANDOFF.md), 배포 비교·절차는 [DEPLOYMENT.md](DEPLOYMENT.md)에 있습니다.

카카오 실제 인가·포트원 테스트 승인/취소·공급자 서명 샘플·실기기 복귀는 자격 증명/외부 테스트 환경이 없어 실행하지 않았습니다. 테스트는 업무 경계 모의이며 공급자 실연동 성공을 보증하지 않습니다.

1. 유료 콘텐츠·정책·미성년자 절차·보존 정책을 확정하고 남은 생성/운영 기능을 구현합니다. 판매 차단은 그 후 테스트 환경에서만 해제합니다.
2. 카카오 앱 REST API 키·client secret·플랫폼·로그인·정확한 콜백 URI·실제 동의항목·심사용 테스트 계정을 준비합니다. 서버 scope와 정책 수집 항목을 대조합니다.
3. 포트원 V2 secret·별도 webhook secret·storeId·카드/카카오/토스 테스트 채널, JSON 웹훅 버전·URL을 준비합니다. 계약상 사용 가능 수단·필수 고객 항목·부분취소를 확인합니다.
4. DB 공급자·서울 등 실제 리전 선택 여부·접속 TLS·역할 분리·백업/복구·연결 제한·위탁/국외 이전을 결정합니다. 로컬 Compose와 실제 PG 테스트는 운영과 분리합니다.
5. 실제 도메인·HTTPS·Vercel/API 프록시 구조·FRONTEND_ORIGIN·SameSite·Secure·등록 콜백을 함께 확정합니다.
6. 대표가 유선전화·고객센터 이메일·통신판매업 정보·정책 버전·공개 전문을 확정합니다. PG 검사와 카드사 심사는 실제 콘솔에서 다시 확인합니다.
7. 검증된 관리자만 제한된 운영 DB 절차로 ADMIN에 지정하고, 환불 담당자·증빙 확인·타임아웃 복구·3영업일 SLA·사고 대응 절차를 마련합니다.

자세한 실행·복구·준비값과 공식 출처는 [운영 문서](OPERATIONS.md)에 있습니다.
