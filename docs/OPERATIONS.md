# 운영·외부 설정·남은 결정

## DB 선택

**PostgreSQL을 기본안으로 선택했습니다.** 로컬 Compose와 PostgreSQL 17용 Testcontainers 설정을 제공합니다. 최신 메이저라는 의미는 아닙니다. 초기 관계형 업무에서 결제·상품 권한·열람·환불을 같은 DB 트랜잭션으로 묶기 쉽고, UUID·시각·제약과 Flyway를 바로 활용할 수 있습니다.

| 기준 | PostgreSQL | MySQL 8.4 + InnoDB |
|---|---|---|
| 주문·결제 원자성 | 트랜잭션·행 잠금·유일 제약 사용 | 동일한 업무 요구를 충족 가능 |
| 경합 제어 | `SELECT ... FOR UPDATE`를 명시 | 잠금 읽기 지원, 격리수준/인덱스 잠금 차이 검토 |
| Spring·이관 | Spring JDBC·Flyway 공식 통합 | 동일 도구 사용 가능, UUID·시각·DDL 이식 필요 |
| 초기 운영 | 단일 DB로 시작, 풀 크기·백업 관리 필요 | 기존 팀 운영 경험이 있다면 유효한 대안 |
| 비용·관리형 | 공급자·리전·백업·연결 옵션에 따라 결정 | 마찬가지로 계약/공급자별 확인 필요 |

MySQL로도 충분하지만 기존 백엔드 스키마나 운영 선호가 없어서 PostgreSQL로 결정했습니다. 특정 무료 제공량·가격·국가별 리전을 가정하지 않았습니다. 관리형 DB는 운영 부담을 줄일 수 있으나 예산·백업 복구·접속 제한·연결 수·위탁·국외 이전을 별도로 결정해야 합니다. [PostgreSQL 잠금 문서](https://www.postgresql.org/docs/current/explicit-locking.html), [MySQL 잠금 읽기 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).

`V1__initial.sql`에 서비스·주문·동의·권한·환불·수신기록·JDBC 세션을 정의했습니다. `TIMESTAMP WITH TIME ZONE`과 서버 UTC Clock을 사용하고 JDBC의 Instant는 UTC OffsetDateTime으로 바꿉니다. 동일 회원의 작업을 회원→주문→환불 순서로 잠가 탈퇴/생성, 열람/환불, 결제 완료/웹훅 경합을 직렬화합니다. 초기 서비스에 단순한 대신 동일 회원의 병렬 처리량이 제한됩니다. 포트원 GET 중 잠금은 최대 8초 응답 제한의 영향을 받습니다. 부하 증가 시 트랜잭션 밖 조회+검증된 스냅샷 적용으로 개선할 수 있습니다.

운영에서는 앱 역할과 마이그레이션 역할 분리, SSL `sslmode=verify-full`, 사설망/IP 제한, 암호화된 백업과 복구 훈련, 비밀 관리 서비스, 연결 수 제한을 적용해야 합니다. Compose의 localhost 비밀번호는 로컬 전용입니다. 현재 작업에서 DB/계정을 만들지 않았습니다. `postgres:17` 이미지의 정확한 패치/digest 고정은 운영 검증 때 결정합니다.

## 상태·환불 복구

주문 상태:

- `CREATED → READY`: 서버 준비값 발급.
- `PENDING`: READY/승인대기 등 포트원 상태를 아직 유료 권한으로 확정할 수 없음.
- `FAILED`, `CANCELLED`: 미승인 상태. 뒤늦게 서버 재조회에서 PAID로 확인되면 재검증 후 반영.
- `PAID`: 검증 완료. 권한만 생성하며 열람 시각은 비어 있음.
- `REVIEW_REQUIRED`: 금액/통화/상점/주문 불일치 또는 미연결 취소. 자동 부여하지 않고 기존 권한도 정지.
- `PARTIALLY_REFUNDED`, `REFUNDED`: 개별 취소 ID와 금액·누적 취소금액이 일치한 상태.

REST 오류는 주문을 PAID로 만들지 않습니다. `/complete` 또는 관리자 재조회·웹훅 재시도로 복구합니다. 자동 장기 재조회 스케줄러/알림은 아직 없습니다. 운영자는 오래 남은 READY/PENDING·CONTENT_PENDING·REVIEW_REQUIRED·UNKNOWN을 주기적으로 확인해야 합니다.

탈퇴 후 지연 승인이 확인되면 삭제 데이터를 복원하지 않고 `REVIEW_REQUIRED`와 결과 미제공 환불 신청을 생성하여 운영자 대기열에 남깁니다. 동일 승인 재수신으로 신청을 중복 생성하지 않습니다.

환불: `REQUESTED → PROCESSING → SUCCEEDED`, 거절은 `REJECTED`, 응답 유실·불확실한 실패는 `UNKNOWN`입니다. 취소 실행 전에 예약과 처리 상태를 DB에 커밋합니다. 중복 process는 차단합니다. API 성공 응답에서도 `SUCCEEDED|REQUESTED|FAILED`를 구분하며, 최종 권한 철회는 포트원 GET의 취소내역으로 확인합니다. 포트원 취소 요청에 `currentCancellableAmount`를 보내 잔액 변동을 검증하고 HTTP POST 자동 재시도는 하지 않습니다.

응답 유실·프로세스 중단으로 cancellationId를 저장하지 못했으면 운영자가 콘솔에서 취소 내역을 확인한 뒤 관리자 reconcile에 제출합니다. 서버는 취소 ID·금액·상점·원 결제와 `SUCCEEDED`를 확인합니다. 누적 취소 잔액만으로 특정 환불의 성공을 추정하지 않습니다. 기록된 부분환불 후 예상하지 못한 추가 취소도 권한을 정지합니다.

콘솔 취소 시 먼저 서버에 환불 신청이 있어야 상품별 예약을 연결할 수 있습니다. 서버 신청 없이 외부에서 발생한 취소는 `REVIEW_REQUIRED`로 차단하며, 상품 매핑과 보상 판단은 운영자 사고 처리 대상입니다. 임의로 권한을 재활성화하면 안 됩니다. 정상 partial 이후 예외로 남은 잔액을 환불할 수 있고 이미 환불된 금액은 다시 지급하지 않습니다.

## 환불 규정 적용과 운영자 확인

- 정상 단순변심/입력오류: 포트원 `paidAt`에서 **168시간 이내(경계 포함)**, 상품 미열람. 비교는 UTC Instant이고 고객 표시 시간대는 Asia/Seoul입니다. 달력상 결제일을 포함한 7일과는 다를 수 있어 사업자 확인이 필요합니다.
- 패키지: `floor(3790 × 미열람 단건가 합계 / 5790)`, 전부 미열람은 3790. 문서의 8개 경우를 테스트했습니다. 초기 상품가는 마이그레이션으로 고정되어 있으며 가격 변경 시 주문/환불 가격 스냅샷 정책을 새 버전으로 이관해야 합니다.
- 미제공·중복결제·시스템 장애: 정상 7일·미열람 제한을 자동 적용하지 않고 심사 접수. 운영자가 결제/공급 증빙을 확인하여 환불/재제공 선택을 처리합니다. 재제공 선택·고객 연락은 고객센터 절차입니다.
- 안내와 다른 결과: 문서의 **제공받은 날부터 3개월, 안 날/알 수 있었던 날부터 30일** 기준을 운영자가 증빙으로 확인합니다. 서버는 ‘인지한 날’을 알 수 없어 이를 검증했다고 주장하지 않습니다. 자동 기간 판정 대신 별도 심사 사유로 구분했습니다.
- 미성년자 동의 없는 결제: 일반 변심과 별도 사유로 접수하여 법정대리인·동의 사실·예외를 운영자가 검토합니다. 체크박스만으로 동의 증명을 완료하지 않습니다.
- 접수 후 3영업일 안내/취소 기준은 휴일 달력·증빙 처리와 함께 운영자가 관리합니다. 자동 영업일 마감/알림은 미구현입니다. 고객센터 시스템에서 SLA 담당자와 영업일 기준을 정해야 합니다.
- 서비스 종료 30일 전 안내·미열람 환불은 종료 계획을 사업자가 정할 때 일괄 절차가 필요합니다. 자동 일괄 환불 작업은 없습니다.

위는 첨부 초안을 반영한 개발 요구사항입니다. 청약철회 제한·예외·기산점·고지의 법적 적합성을 보증한 것이 아니며 법률 검토와 운영 승인 후 확정해야 합니다.

## 카카오·나이·탈퇴

카카오 REST 인가 코드 흐름을 Spring Security로 구현했습니다. 필요한 값은 REST API 키, 클라이언트 시크릿, 등록한 리다이렉트 URI, 앱 플랫폼/로그인 활성화입니다. 이메일·닉네임·생일 scope를 임의로 요청하지 않고 회원번호만 식별에 사용합니다. 실제 수신 가능한 나이/생년 정보는 앱의 동의항목·자격·사용자 동의에 따라 확인해야 합니다. 현재 서버는 인증된 나이를 받지 않으므로 나이 검증을 완료한 상태로 기록하지 않습니다. AGE14_SELF_DECLARED는 자기 신고만 뜻합니다. KCP 본인인증은 구현하지 않았습니다.

만 14세 미만 거절 UI·확인 방법, 타인의 생일로 분석하는 경우와 계정 소유자의 나이 구분, 만 19세 미만 결제 시 법정대리인 동의 절차·증빙·철회·보관 범위를 사업자가 결정해야 합니다. 현재는 필수 자기 신고·안내와 예외 환불 접수 경계까지 제공합니다.

로그아웃은 **현재 서비스 세션** 종료입니다. 카카오계정 전역 로그아웃이 아닙니다. 탈퇴는 서비스 결과·동의·선택 입력과 카카오 회원번호를 삭제하고 모든 서비스 세션을 폐기합니다. 이전 세션이 남더라도 매 요청 계정 상태를 다시 확인합니다. 진행 중 환불은 거래기록에 보존하여 탈퇴 후에도 운영자가 처리할 수 있습니다. 미열람 환불 가능성을 먼저 보여주고, 신청번호·고객센터 안내를 남기는 탈퇴 전 UI가 필요합니다.

카카오 앱 연결 해제(토큰 폐기) API는 이번 구현에 포함되지 않았습니다. 서비스 데이터 삭제와 카카오 연결 해제는 별도입니다. 원격 연결 해제·카카오 측 탈퇴 콜백을 운영하려면 실패 시 재처리와 개인정보 보관 근거를 포함해 후속 구현이 필요합니다. 카카오 access token을 프론트나 업무 DB에 저장하지 않습니다. OAuth 클라이언트가 사용하는 서버 메모리 내 토큰은 프로세스 수명/공급자 만료를 따르며 전용 영구 토큰 저장소를 추가하지 않았습니다.

## 쿠키·Vercel·보안

`YHDSESSION`은 HttpOnly, 기본 Secure, host-only입니다. CORS는 `CORS_ALLOWED_ORIGINS`의 정확한 Origin 목록을 허용하고 credentials를 켭니다. 기본값은 `https://yeonhakdang.vercel.app,http://localhost:3000`입니다. `FRONTEND_ORIGIN`은 로그인·결제 복귀 목적지 하나를 정하는 별도 설정이며 CORS 목록으로 사용하지 않습니다. 모든 변경 API는 세션 CSRF 헤더를 검사하며 웹훅은 원문 서명을 검사합니다. JSON 64KiB 제한, DTO 검증, 매 요청 계정·관리자 역할 확인, 본인 소유권 확인, `Cache-Control:no-store`, 일반화된 오류를 적용했습니다.

- 로컬: localhost:3000→localhost:8080, `COOKIE_SECURE=false`, SameSite=Lax, credentials 포함.
- 권장 운영 구조: 예를 들어 같은 등록 도메인의 app/api 하위 도메인 또는 same-origin 리버스 프록시. 실제 도메인은 미정입니다. Lax 쿠키와 정확한 CORS·HTTPS·콜백 URI를 함께 확인합니다.
- vercel.app와 완전히 다른 API 사이트: cross-site fetch에는 `COOKIE_SAME_SITE=None`, Secure=true가 필요할 수 있지만 브라우저의 제3자 쿠키 차단 때문에 동작을 보장하지 못합니다. HTTPS same-origin 프록시 또는 같은 사이트 도메인을 우선 결정하세요.
- OAuth 최상위 GET 복귀는 Lax와 호환되지만 Safari·카카오 인앱 브라우저·로그인 전후 CSRF 회전·PG 모바일 복귀를 실제 기기에서 검증해야 합니다. 세션 ID를 localStorage나 URL로 전달하지 않습니다.

결제 원문/카드번호·생일·출생시간·쿠키·비밀키를 애플리케이션 로그에 출력하지 않습니다. 외부 오류 본문도 응답/로그에 복사하지 않습니다. 운영 프록시·APM·Vercel Analytics·접속 로그의 URL/헤더/본문 마스킹은 인프라 설정에서 확인해야 합니다. 요청 본문·SQL 바인딩 TRACE 로그를 활성화하지 마세요. 비밀값은 환경변수로 주입하고 공개 `NEXT_PUBLIC_*`에 넣지 않습니다. 요청 제한·WAF·운영 감사 로그·SLA 알림은 배포 인프라 후속 사항입니다.

## 개인정보·보존

업무 DB는 카카오 식별자와 최소 결과 요약만 받고 원본 이름·생일·출생시간·성별·카드번호를 받지 않습니다. 결과 요약도 개인과 연결된 정보이므로 개인정보 접근 통제를 적용해야 합니다. 유료 콘텐츠 등록 시 운영자가 원본 개인정보를 불필요하게 넣지 않도록 콘텐츠 스키마·검수를 확정해야 합니다.

탈퇴 시 결과 요약·유료 원문·동의 행·대학/관계 입력·카카오 회원번호를 제거하고 거래 UUID·상품·금액·상태·시각·결제 ID·구매 동의 버전/시각·최초열람/환불 증거를 보존합니다. UUID 연결 stub은 거래기록용이며 재로그인 계정과 자동 연결하지 않습니다. 분쟁·환불 대응에 추가 식별 근거가 필요한지는 운영·법률 검토 사항입니다.

첨부 방침의 보존안은 계약/청약철회·대금/공급 5년, 불만/분쟁 3년, 방문기록 3개월입니다. 이를 법률 검증 완료로 간주하지 않았습니다. 현재 보존 기록의 기간 만료 자동 파기 작업·분쟁 법적 보존 예외·백업 만료 연동·동의 증거 보관 범위는 미구현입니다. 운영 전 항목별 보존 근거·기산일·보존 책임자와 파기 작업을 확정하고 구현해야 합니다. 원본 방침에 없는 ‘무기한 보관’을 운영 정책으로 쓰면 안 됩니다.
